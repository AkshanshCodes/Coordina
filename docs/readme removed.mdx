## Native graph engine

The task dependency graph is backed by a native C++ graph engine in `src/graph-engine`. The API consumes it through an `IGraphEngine<Guid>` port, so board pages use one cycle-safe relationship engine while the native implementation can evolve independently.

text
src/graph-engine
├── include/coordina_graph_engine.h  # Stable C ABI consumed by .NET
└── src
    ├── core/                        # Node/edge types, immutable graph snapshot
    ├── algorithms/                  # Traversal, cycle-safe validation, topological
    │                                # order, critical path, node analysis, suggestions
    ├── planning/                    # Shared board analysis (planning_analysis), next-task
    │                                # ranking (work_planner), score rules (work_score)
    └── interop/                     # C ABI exports and array conversion helpers


Layers depend inward only: `core` ← `algorithms` ← `planning` ← `interop`.

The board planning view uses one native call, `coordina_graph_analyze_board`, which builds the graph once and returns readiness, dependency order, critical path, node analyses, and ranked work together. It reports an explicit status (`OK`, `INVALID_ARGUMENT`, `INSUFFICIENT_CAPACITY`) separately from output counts. `make graph-engine-benchmark` compares this batch call with the individual calls. Includes are rooted at `src/graph-engine/src` (for example, `#include "algorithms/critical_path.h"`).

## Project module: lifecycle and permissions

Projects are the first structured work layer inside a workspace. V2 adds lifecycle status, project ownership, metadata, audit fields, and soft deletion.


### Lifecycle states

| Status | Behavior |
| --- | --- |
| `ACTIVE` | Default status, returned by the default list endpoint |
| `ARCHIVED` | Hidden by default; returned with `includeArchived=true` |
| `COMPLETED` | Hidden by default; returned with `includeCompleted=true`; read-only |

### Permission model

| Action | Server-side rule |
| --- | --- |
| Create project | Authenticated workspace member |
| List and view projects | Authenticated workspace member |
| Project details | Authenticated workspace member; project ID is scoped by workspace ID |
| Edit project | Workspace `OWNER` or project owner, unless completed |
| Archive project | Workspace `OWNER` or project owner, unless completed |
| Restore project | Workspace `OWNER` or project owner |
| Permanent delete | Workspace `OWNER` only |

### Card completion behavior

| Action | Result |
| --- | --- |
| Create or move a card into a `DONE` list | The card is completed |
| Move a card out of a `DONE` list | The card is reopened |
| `PATCH` a card with `isCompleted: true` | The card moves to the board's first `DONE` list |
| `PATCH` a card with `isCompleted: false` | The card moves to the board's first `TODO` list |
| No list with the target status | `409 Conflict`; card remains unchanged |

### Card fields

| Field | Notes |
| --- | --- |
| `id` | Server-generated card ID |
| `boardId` / `listId` | Mandatory board/list placement |
| `title` | Required, 180 characters or fewer |
| `description` | Editable in the side panel |
| `priority` | Optional `LOW`, `MEDIUM`, or `HIGH` |
| `dueDate` | Optional date shown compactly on cards |
| `labels` | Small colored tags for scanning |
| `isCompleted` / `completedAt` / `completedBy` | Kept consistent with the list's `taskStatus` |
| `assignees` | Multiple workspace members |
| `createdAt` / `updatedAt` | Server-managed audit timestamps |

### Future expansion

The project shell reserves space for future modules. The Docs tab is a placeholder for a Notion-like document system, and Settings is isolated from task board state. Future modules should follow the same pattern: project shell for layout/navigation, feature modules for their own contracts, API client, state, and UI.

The board contracts are prepared for possible realtime updates, comments, attachments, notifications, and activity logs. These features are not implemented yet; they should attach to board/card identifiers rather than changing the project shell.

## 11. Documentation site setup

Mintlify should be configured as a monorepo deployment with documentation path `/docs`. The web app redirects `/docs` to `VITE_DOCS_URL`, while the API serves the local OpenAPI tester at `/api-docs`.

The documentation site can be run locally with:

```bash
make docs
```
